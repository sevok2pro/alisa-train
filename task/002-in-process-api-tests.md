# Задание 002 — API-тесты без отдельного процесса

Статус: **в работе**

## Цель

Отделить создание HTTP-приложения от запуска серверного процесса и настроить API-тесты напрямую через жизненный цикл `node:test`.

## Контекст

В задании 001 отдельный дочерний процесс помог разобраться с запуском, готовностью, кодами выхода и очисткой. Но для обычных API-тестов такая оркестрация не обязательна. Сейчас runner все еще зависит от `netstat` и `findstr`, вручную ищет порт и заменяет окружение дочерних процессов.

Сервер можно создавать внутри тестового процесса. Тогда ОС сама выделит свободный порт, а `node:test` поможет гарантированно освободить ресурсы. Отдельный процесс позже пригодится для end-to-end проверки настоящего production-запуска.

## Что нужно сделать

1. Разделить код создания HTTP-сервера и код его запуска на прослушивание порта. Точка входа `npm run run` должна только собирать и запускать приложение.
2. Перевести стандартный `npm test` на запуск тестов через возможности `node:test`, без собственного orchestration-runner и дочерних процессов.
3. Поднимать тестовый сервер через test lifecycle hooks. Для каждого полного прогона должно создаваться чистое состояние приложения.
4. Передать ОС выбор свободного порта и получить фактический адрес из запущенного сервера. В тестах не должно быть поиска порта через внешние утилиты.
5. Гарантировать закрытие сервера после тестов, включая failed test, без завершения процесса через `process.exit()`.
6. Сохранить существующие API-сценарии, `/ping` и поведение `npm run run` для обычного запуска.
7. Убрать ставший ненужным код оркестрации из стандартного пути проверки.
8. Заполнить раздел «Результат» после самостоятельной проверки.

## Ограничения

- Не добавлять backend-фреймворк, тестовый фреймворк или новые зависимости.
- Не подключать базу данных.
- Не менять HTTP-контракт существующих endpoint и ожидания тестов.
- Не превращать задание в общий рефакторинг валидации или хранения: они будут отдельными задачами.
- Код изменяет пользователь самостоятельно.

## Темы для исследования

- Composition root: где приложение создается и где запускается.
- Побочные эффекты при импорте модуля и почему `listen()` при импорте мешает тестам.
- Порт `0` в `server.listen()` и получение адреса через `server.address()`.
- Hooks `before`/`after` в `node:test` и их выполнение при failed test.
- Асинхронное закрытие `http.Server` и открытые keep-alive соединения.
- Согласование адреса прослушивания `127.0.0.1` и URL тестов без неоднозначности `localhost`/IPv6.

## Критерии приемки

- `npm run ts:check` проходит.
- `npm test` работает без предварительно запущенного приложения и без дочерних процессов.
- Два последовательных `npm test` успешны, все прежние 9 API-сценариев сохранены.
- Тестовый сервер получает свободный порт от ОС; запросы идут на фактически выделенный адрес.
- Сервер закрывается после успешных и failed тестов; `process.exit()` для управления тестами не используется.
- `npm run run` по-прежнему запускает приложение, а `/ping` отвечает `200`.
- В стандартном тестовом пути больше нет `netstat`, `findstr`, `exec`/`spawn` и ручного ожидания готовности.
