# Задание 003 — пользователи в PostgreSQL через Docker

Статус: **в работе; первый шаг — настройка Docker**

## Цель

Заменить хранение пользователей в памяти на PostgreSQL, который запускается через Docker Compose. Результат: зарегистрированный пользователь сохраняется после перезапуска приложения и контейнера БД, а параллельные регистрации одного логина не создают дубликаты.

Задание 002 временно отложено. Текущий тестовый runner можно сохранить; перестройка формата тестов сейчас не требуется.

## Шаг 0. Подготовить окружение

В текущем окружении Docker не обнаружен: команда недоступна, стандартная установка и служба Docker Desktop не найдены.

1. Самостоятельно установить Docker Desktop на Windows с WSL 2, следуя официальной документации.
2. Запустить Docker Desktop и убедиться, что работают `docker version` и `docker compose version`.
3. Разобраться в разнице между образом, контейнером, volume и Compose service до настройки проекта.

Если установка заблокирована политиками Windows/WSL, зафиксировать конкретную ошибку в результате и сообщить наставнику — не заменять Docker скрытой локальной установкой PostgreSQL.

## Что нужно сделать

### 1. PostgreSQL в Docker Compose

- Добавить Compose-конфигурацию для PostgreSQL с зафиксированной основной версией образа, healthcheck и named volume.
- Настроить локальные учетные данные и подключение через переменные окружения. Не коммитировать реальные секреты; файл локальных секретов должен быть исключен из Git.
- Предусмотреть понятные команды запуска и остановки БД и способ проверить её готовность.
- Не использовать `latest` и не хранить данные только внутри временного слоя контейнера.

### 2. Схема и миграция

- Создать SQL-миграцию для таблицы пользователей: идентификатор, уникальный логин, хеш пароля и время создания.
- Применение миграций должно быть отдельным воспроизводимым шагом, а не скрытым побочным эффектом обработки HTTP-запроса.
- Повторный запуск начальной миграции не должен разрушать данные или делать окружение неработоспособным.
- Предусмотреть отдельную тестовую БД, чтобы очистка тестов не удаляла данные ручной разработки.

### 3. Подключение приложения к БД

- Использовать PostgreSQL через SQL и пул соединений; ORM пока не добавлять.
- Вынести параметры подключения в конфигурацию окружения и передать их серверу в тестовом runner без потери остального окружения.
- Перевести регистрацию и вход на запросы к БД, сохранив текущие HTTP-ответы и хеширование паролей.
- Все значения пользователя передавать параметризованными запросами, без подстановки в SQL-строку.
- Уникальность логина должна гарантироваться ограничением БД. Предварительная проверка существования логина не заменяет ограничение: между проверкой и вставкой возможна гонка.
- Ошибку уникальности преобразовать в существующий ответ `409`; остальные ошибки БД не должны раскрывать SQL, хеши или внутренние детали клиенту.

### 4. Проверки

- Сохранить существующие 9 API-тестов и адаптировать их окружение к реальной БД.
- Обеспечить изоляцию и повторяемость тестов через отдельную тестовую БД и явную очистку/подготовку данных.
- Добавить сценарий одновременной регистрации одинакового логина: допустим только один созданный пользователь, второй запрос получает `409`, в таблице одна запись.
- Запустить проверку типов и два полных тестовых прогона.

### 5. Ручная демонстрация результата

- Запустить БД, применить миграцию и стартовать приложение.
- Зарегистрировать нового пользователя.
- Перезапустить приложение и контейнер PostgreSQL, дождаться готовности БД.
- Успешно войти тем же пользователем.
- Через `psql` внутри контейнера убедиться, что запись существует, логин хранится один раз, а открытого пароля в таблице нет.

## Ограничения

- Не добавлять ORM, backend-фреймворк или новый тестовый фреймворк.
- Не менять существующий JSON-контракт `/register` и `/login`.
- Не использовать production-секреты и не выводить пароли либо их хеши в логи.
- Не выполнять миграции автоматически при каждом HTTP-запросе.
- Код и команды настройки выполняет пользователь самостоятельно.

## Темы для исследования

- Docker Compose services, healthcheck, named volumes и жизненный цикл данных.
- PostgreSQL roles, databases, `TEXT`/`VARCHAR`, identity и `UNIQUE`.
- Пул соединений `pg`, параметризованные запросы и освобождение клиентов.
- SQL migrations и отличие миграции от создания таблицы при старте приложения.
- Код ошибки PostgreSQL при нарушении уникальности и race condition при check-then-insert.
- Переменные окружения и наследование `process.env` дочерним процессом.

## Критерии приемки

- `docker version`, `docker compose version` и запуск PostgreSQL работают.
- Миграция применяется отдельной документированной командой и безопасна при повторном запуске.
- Регистрация и вход используют PostgreSQL, открытые пароли не сохраняются.
- Пользователь сохраняется после перезапуска приложения и контейнера БД.
- Одновременные регистрации одинакового логина не создают дубликаты; нарушение уникальности дает `409`.
- Тесты используют отдельную БД, не удаляют dev-данные и дважды проходят без ручной очистки.
- `npm run ts:check` проходит; существующие API-сценарии и новый конкурентный сценарий успешны.
- В Git нет локальных секретов и данных volume.
