# Задание 001 — воспроизводимая проверка API

Статус: **в работе**

## Цель

Сделать проверку текущего HTTP API самостоятельной и повторяемой: разработчик или CI должен получать достоверный результат одной стандартной командой, без отдельно запущенного сервера и без влияния предыдущих запусков.

## Почему это важно

Сейчас `npm test` обращается к фиксированному `localhost:4200`, но сам сервер не поднимает. Тест также зависит от состояния, оставшегося от предыдущих запусков. Такой сценарий может неожиданно падать или, наоборот, проверять чужой процесс на том же порту. До развития API нужно научиться доверять его проверкам.

## Что нужно сделать

1. Настроить стандартную команду проверки TypeScript без генерации выходных файлов.
2. Изменить организацию запуска приложения и тестов так, чтобы `npm test` самостоятельно подготавливал окружение, запускал проверки и освобождал ресурсы.
3. Устранить зависимость тестов от заранее запущенного сервера, фиксированного свободного порта и данных прошлых запусков.
4. Сохранить существующие проверки регистрации и входа. Их назначение и ожидаемый HTTP-контракт не должны меняться ради упрощения решения.
5. Убедиться, что после тестов не остается процесс, удерживающий порт.
6. Запустить проверки повторно и зафиксировать в разделе «Результат» выполненные команды и наблюдения.

## Ограничения

- Не добавлять backend-фреймворк и новую тестовую библиотеку: текущих Node.js, TypeScript и `node:test` достаточно.
- Не подключать базу данных и не менять бизнес-правила API.
- Не ограничиваться проверкой компиляции: тесты должны выполнять реальные HTTP-запросы к экземпляру приложения.
- Код изменяет пользователь самостоятельно.

## Темы для исследования

- Жизненный цикл `http.Server`: создание, начало прослушивания порта и закрытие соединений.
- Динамическое выделение порта операционной системой и получение фактического адреса сервера.
- Хуки жизненного цикла и области видимости тестов в `node:test`.
- Асинхронное завершение ресурсов и поведение при ошибке в процессе проверки.
- Разница между запуском приложения как отдельного процесса и использованием его из тестового процесса.

## Критерии приемки

- `npm test` успешно работает при предварительно остановленном приложении.
- Два последовательных запуска `npm test` дают одинаково успешный результат без ручной очистки состояния.
- Проверка TypeScript доступна отдельной npm-командой и проходит без ошибок.
- Во время тестов выполняются реальные запросы к созданному ими серверу.
- После завершения тестов сервер закрыт, включая сценарий с failed test.
- Существующие API-сценарии сохранены и проходят.

### Блокирующее замечание

После каждого прогона остается новый процесс `node apps/server/index.ts`, который продолжает слушать порт. Всего до проверки уже было пять таких процессов; проверка добавила еще по одному на прогон. Процессы, созданные проверкой наставника, после этого остановлены; ранее существовавшие пользовательские процессы не завершались.

Причина связана с комбинацией `exec`, `kill()` и немедленным `process.exit()` в `apps/server/testRunner.ts`: `exec` запускает команду через shell, поэтому завершение наблюдаемого shell-процесса не гарантирует завершение его дочернего Node.js-процесса. Родитель также не дожидается подтверждения завершения сервера.

Направление для исправления: пересмотреть запуск Node.js без промежуточного shell и построить единый путь завершения, который сначала останавливает дочерние процессы, дожидается их завершения и только затем завершает runner с кодом результата тестов. Этот путь должен работать и при failed test, и при ошибке запуска.

### Остальные замечания

1. `setTimeout` на две секунды не подтверждает готовность сервера. На медленной машине тесты начнутся слишком рано, а при быстром падении сервера пауза только отложит ошибку. Нужно исследовать событие фактического начала прослушивания порта и ранний выход дочернего процесса.
2. `netstat` + `findstr` привязывает runner к Windows; любая ошибка команды считается признаком свободного порта. Между проверкой и `listen()` также возможна гонка. Исследуй выделение свободного порта самой ОС и передачу фактического адреса тестам.
3. Полностью замененный `env` удаляет остальные переменные окружения дочерних процессов. Проверь, как безопасно добавить `SERVER_PORT` к текущему окружению.
4. Обработчики `error` только выводят ошибку, но не обеспечивают завершение остальных процессов и ненулевой результат runner.

Для повторной проверки после исправлений: остановить оставшиеся от своих экспериментов серверы, выполнить `npm run ts:check` и два `npm test`, затем убедиться, что новых серверных процессов не осталось.
